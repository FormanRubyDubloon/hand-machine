# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

`hand-machine` is the build side of Isaac Forman's Hand & Machine study: what is the human designer for when a machine can generate the interface? The working thesis is that AI makes production cheap, so value moves to judgement, taste, framing the problem, knowing the user, and taking responsibility. This repo is where that thesis gets tested in practice: experiments, prototypes and components made with AI tools.

What this means for working here:

- **Isaac is a senior product designer (20+ years) and a self-described vibe coder.** He doesn't need design basics explained, but he does want code changes explained in plain terms: what changed, why, and what to check.
- **Design decisions are his.** When a change involves a visual or interaction choice (spacing, colour, hierarchy, copy, behaviour), offer a recommendation with the trade-offs rather than quietly picking one. Those choices are the point of the study.
- **Note what the AI got wrong.** If generated code or design needed correcting, or a tool hit a limit, say so briefly. These notes feed the essay and talk.
- **Plain, direct English.** No inflated phrasing or jargon metaphors.

## Overview

A design system foundation: a Vite + React 19 + TypeScript app styled with Tailwind CSS v4 and shadcn/ui (style `radix-sera`, base colour `taupe`, lucide icons). `src/App.tsx` is a component showcase page, not an application. The package manager is **pnpm**.

## Commands

- `pnpm dev`: Vite dev server (port 5173, see `.claude/launch.json`)
- `pnpm build`: `tsc -b && vite build`
- `pnpm lint`: `oxlint` (config in `.oxlintrc.json`; there is no ESLint)
- `pnpm storybook`: Storybook on port 6006. `pnpm build-storybook` builds it.
- Tests: there is no `test` script; run `pnpm exec vitest run`. Two projects: `storybook` runs every story as a browser test (Chromium via Playwright, `@storybook/addon-vitest`; one story with `pnpm exec vitest run --project storybook -t "<story name>"`), and `claude-connection` runs the MCP server's tests in Node. Confirmed working 15 November 2026 (162 tests, about 8 seconds).
- Add shadcn components with `pnpm dlx shadcn add <name>` (configured via `components.json`).
- `pnpm build:mcp`: bundles the Claude connection's server into `supabase/functions/mcp/index.js`. Deploy it with `supabase functions deploy mcp --use-api --no-verify-jwt`.

## Architecture

- **Path alias:** `@/*` → `src/*`, defined in both `vite.config.ts` and `tsconfig.app.json`. Keep them in sync.
- **Theming:** all tokens live in `src/index.css`. Colours are CSS variables on `:root` (oklch values) and mapped into Tailwind by the `@theme inline` block (`--color-*`); don't wrap them in `hsl()`. Dark mode uses `@custom-variant dark (&:is(.dark *))`, i.e. a `.dark` class on an ancestor.
- **shadcn CLI:** the root `tsconfig.json` must carry the `@/*` path alias, otherwise `shadcn add` writes into a literal `@/` folder. After adding or overwriting components, check they import `cn` from `@/lib/utils` (the CLI has emitted `from "cn"`, the unrelated npm package) and that stock `radix-sera` styling (square corners, uppercase buttons) is intact. `shadcn add` also rewrites `src/index.css` fonts (to Noto Sans and Playfair Display), `src/lib/utils.ts` and `button.tsx`, and re-adds the `cn` and `@fontsource-variable/*` packages. Revert those and keep only the new component files (`git checkout` them, then fix the `cn` import).
- **Components:** `src/components/ui/` holds shadcn primitives built on `radix-ui`, `class-variance-authority`, and the `cn()` helper in `src/lib/utils.ts`. Each component has a `<name>.stories.tsx` beside it; add one when you add a component.
- **Storybook:** config in `.storybook/`. Stories sort Foundations (`src/foundations/`: colour, typography, spacing, shape, motion) before UI. The Theme toolbar toggles the `.dark` class on `<html>` so portalled content (dialog, select, tooltip) follows. The a11y addon is set to `todo`, so violations show but don't fail tests.
- **Figma mirror:** `GAPS.md` records where Figma can't match the code (oklch to sRGB, `calc()` radii as fixed px, invented primitive names). Update it whenever Figma and code diverge. `src/index.css` is the source of truth for tokens.
- **Prototypes:** experiments live in `prototypes/<name>/`, each with its own `index.html` served by the root Vite app at `/prototypes/<name>/` (add it to `build.rollupOptions.input` in `vite.config.ts`; `tsconfig.app.json` includes `prototypes/*/src`). Prototypes import from `@/components/ui`. `prototypes/shopping-list` is the first: a phone web app that syncs with the pantry's `items` in Supabase (`src/remote-pantry.ts`), state in localStorage. It follows `prototypes/shopping-list/HANDOFF.md` and `intent.md`; read `intent.md` before changing it. Pieces the handoff marks "new" live in `prototypes/shopping-list/src/components.tsx`, not in `src/components/ui`. `prototypes/pantry-app` is the second: the desktop pantry admin app, built to its own `HANDOFF.md` and the same `intent.md`. Both prototypes start from one seed in `prototypes/shared/src/pantry.ts` and share localStorage: the pantry writes the items the phone syncs with, and the phone pulls stores, aisles and recipes at sync. A "Demo" menu in the pantry header fakes a phone sync with conflicts and resets both apps.
- **Intent:** `prototypes/shopping-list/intent.md` covers the whole system (mobile app, pantry admin app, Claude connection), not only the shopping list. It was last updated on 16 November 2026. A copy is kept as `intent.md` in the Hand & Machine project in Claude; when one changes, update the other.
- **Mobile app (planned, not built yet):** the intent now replaces the phone web app with one native iPhone app, built with Expo (React Native), with three sections: Shopping list, Recipes and Pantry. There is no separate kitchen app; the cooking view is the recipe detail page. No Expo project exists in this repo yet, and where it lives hasn't been decided, so ask before creating one. What the intent fixes: it uses the same Supabase database and sign-in as the other apps; it ships through TestFlight; it runs on iPhone now and may need Android later; sync stays manual for now, with the aim of removing manual sync everywhere later, so don't build anything that makes automatic sync harder. `prototypes/pantry-app/src/model.ts` and `prototypes/shared/src/rows.ts` are already free of React and browser code, so the mobile app can reuse them. shadcn/ui and Tailwind components don't run in React Native, so its screens are rebuilt with native components; the tokens in `src/index.css` carry over as values only.
- **Shopping-list web app is now a fallback:** `prototypes/shopping-list` stays running until the native app takes over, but it isn't being improved. Fix it if it breaks; don't add features to it.
- **Supabase:** the repo is linked to the Supabase project "pantry" (ref `bgwlqmpyjfqsvoqgpdtn`, London) through the CLI (`supabase/config.toml`). `src/lib/supabase.ts` exports a client built from `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` in `.env.local` (gitignored; `.env.example` shows the shape). Only the publishable key goes in `.env.local`, never the service-role key. It was loaded on 14 November 2026 with `categories` (Notion's 18), `items` (140, from the Notion Pantry database), `recipes` (31, from the Notion Recipes pages) and `recipe_ingredients` (421; 310 linked to an item by `item_id`, the rest aren't in the pantry). The apps and Claude have added to them since. See `supabase/migrations/`. Categories have an optional `colour` (one of twelve named hues) and `icon` (a Lucide name), listed in `prototypes/shared/src/category-look.ts` (`20261117120000_category_colour_and_icon`); the hues are tokens in `prototypes/shared/src/category-look.css`, always drawn at `--category-tint` opacity over the background, never solid, so they follow a background change. They're set in the pantry app's Settings → Categories and sync with the category's name. It also holds `stores` and `store_aisles` (one row per store and numbered category; `20261114170000_stores`). Anon can read; signed-in users can read and write items, categories, stores, aisle numbers and recipes (`20261114180000_recipe_writes`). Both prototypes load the items and recipes at startup (`prototypes/shared/src/supabase-seed.ts`, awaited in each `main.tsx`) into the shared seed; the demo items, recipes and history are gone. Recipe ingredients from Notion carry no quantities, so linked ones are stored as partial (any stock will do); unknown serves shows as 2 and unknown time as "No time". The pantry app signs in with Supabase Auth (password or email link, `prototypes/shared/src/auth.ts`; sign-ups are off, accounts are made by hand in the dashboard). It syncs once when it opens with a live session, and has a Sync button. Sync sends item, category, store (with aisle numbers) and recipe changes to Supabase and pulls remote ones (`pantry-app/src/sync.ts`: categories first, then stores, items, recipes, and removed categories are deleted last; only the default store stays local). Recipe sync keeps the columns the app doesn't have (emoji, source link, Notion id, ingredient group names). Writing needs the `20261114140000_auth_and_item_writes` migration and a session. The shopping list signs in the same way (`prototypes/shared/src/auth.ts`, password or email link) and its Sync fetches the items, merges, and writes the result back (`prototypes/shared/src/pantry-remote.ts` holds the row mapping both apps use); a failure to reach Supabase shows the No signal screen. Shopping-list entries (hand-added and recipe ones) are rows in `list_entries`, read with each item and rewritten whenever the item is pushed; the pantry app's History is the `history` table (signed-in read and write only), merged by id at Sync (`syncHistory` in `pantry-app/src/sync.ts`). Both come from `20261115100000_list_entries_and_history`, which drops the old `items.entries` column, so apply it before running the new code. The phone's Sync also pulls categories, stores and aisle numbers from Supabase and pushes store and aisle-number edits made on the phone (`mergeStores` in `prototypes/shopping-list/src/model.ts`: per store, the phone's version wins if it changed since the last sync); only recipes still come from the pantry app through localStorage. 
- **Claude connection:** `prototypes/claude-connection` is the MCP server that lets Claude read and change the pantry (see its `README.md`). It's a Supabase Edge Function (`mcp`) bundled by `pnpm build:mcp` into `supabase/functions/mcp/index.js` (generated; don't edit it). It reuses `prototypes/pantry-app/src/model.ts` and `prototypes/shared/src/rows.ts`, so keep those free of React, `@/` imports and browser globals. A change to either needs `pnpm build:mcp` and a redeploy; `test/bundle.test.ts` fails until the bundle is rebuilt. Sign-in is Supabase Auth's OAuth server (Claude registered by hand as a public app with no secret, dynamic registration off) with a consent page at `/prototypes/claude-connection/`. Edits and deletes refuse without `confirmed: true`, and every change is logged to `history` as `claude`. Its tests run in Node: `pnpm exec vitest run --project claude-connection`.
- **Typeface:** Stevie Sans, loaded from Adobe Fonts via a Typekit stylesheet in `index.html`. `@fontsource-variable/inter` is still imported in `index.css` as a fallback.

## Gotchas

- `README.md` is the unmodified Vite template and doesn't describe this project.
- The parent directory's git repo also tracks the sibling `../fluido` project; work here is scoped to `hand-machine`.
- Netlify (`shopping-list-app-db5118`, settings in `netlify.toml`) isn't connected to GitHub: merging to `main` doesn't deploy. Deploys are started by hand (the Netlify connector or dashboard).
- Supabase CLI 2.75 doesn't push the `[auth.oauth_server]` settings in `config.toml`; they were set in the dashboard. CLI 3 refuses this `config.toml` until it's migrated (`[inbucket]` became `[local_smtp]`).
- Register Claude as a public OAuth app. A confidential one fails after Allow: Claude sends its secret with `client_secret_post`, and Supabase only accepts `client_secret_basic` for it.
